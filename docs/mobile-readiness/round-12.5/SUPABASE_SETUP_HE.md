# הקמת Supabase – הוראות לבעל המוצר

עדיין אין חשבון Supabase, ולכן לא נפתח שום פרויקט ולא הופעל שום שירות בתשלום. זו רשימת הצעדים המדויקת. אחרי שתבצע אותם אוכל להריץ את בדיקות הקבלה על staging אמיתי.

> **לא לייצור.** סנכרון בגרסת הייצור נשאר כבוי. אין לפתוח פרויקט ייצור לפני שאישרת מדיניות פרטיות ולפני שעברו בדיקות הקבלה ב-staging.

## מה צריך להחליט קודם

1. **אזור:** האזור נקבע כשפותחים פרויקט ואי אפשר לשנות אותו אחר כך. ההמלצה: Frankfurt (`eu-central-1`).
2. **תוכנית:**
   - לפיתוח ול-staging: התוכנית החינמית (Free). בתוכנית הזו פרויקט שאין בו פעילות שבוע מושהה.
   - לייצור: Pro בתשלום חודשי. זו החלטה שלך, והיא לא נדרשת עכשיו.
3. **שולח הדוא״ל:**
   - בפיתוח מספיק שרת הדוא״ל המובנה של Supabase. הוא מוגבל לכמה הודעות בשעה.
   - לפני staging עם משתמשים אמיתיים צריך SMTP משלך, למשל ספק דוא״ל טרנזקציוני. זה לרוב בתשלום ודורש את אישורך.

## צעדים

1. **פתיחת חשבון ופרויקטים:**
   - פתח חשבון ב-supabase.com עם דוא״ל של הארגון, לא דוא״ל אישי.
   - צור שני פרויקטים: `mitzvotplus-dev` ו-`mitzvotplus-staging`, באזור Frankfurt ובתוכנית Free.
   - שמור את סיסמת מסד הנתונים במנהל סיסמאות. אל תשלח אותה בצ׳אט ואל תשמור אותה במאגר.
2. **החלת המיגרציות:** מחשב עם [Supabase CLI](https://supabase.com/docs/guides/cli), בתיקיית המאגר:
   ```bash
   supabase login
   ```
   ```bash
   supabase link --project-ref <ה-ref של mitzvotplus-staging>
   ```
   ```bash
   supabase db push
   ```
   הפקודה מחילה את ארבע המיגרציות שבתיקייה `supabase/migrations`, לפי הסדר.
3. **הגדרות התחברות** (בלוח הבקרה: Authentication):
   - **Providers → Email:** מופעל. "Confirm email" כבוי, כי הקוד עצמו מאמת את הכתובת.
   - **Email OTP:** אורך 6 ספרות, תוקף 600 שניות.
   - **Email Templates → Magic Link:** הנושא `קוד הכניסה שלך למצוות+`, והתוכן מתוך הקובץ `supabase/templates/magic_link.html`. בתבנית יש רק את הקוד (`{{ .Token }}`), בלי קישור.
   - **Rate limits:** לפחות 60 שניות בין שני קודים לאותה כתובת.
   - **ספקים אחרים:** Google, Apple ושאר הספקים כבויים. לכן סעיף 4.8 של Apple לא חל.
4. **הגדרות ה-API** (בלוח הבקרה: Data API / API settings):
   - **Exposed schemas:** רק `public`. אסור להוסיף את `private`, כי שם נמצאות פונקציות העזר של הקהילה.
   - **Extra search path:** `public, extensions`.
5. **בדיקת ההרשאות על הפרויקט האמיתי:**
   - בלוח הבקרה, ב-SQL editor, הרץ את שאילתות הביקורת שבסעיף 14 של `scripts/db/test-db.mjs`.
   - התוצאה הנדרשת:
     - לתפקיד `anon` אין שום הרשאה;
     - `authenticated` יכול להפעיל בדיוק 12 פונקציות.
   - אפשר גם להעביר לי מחרוזת חיבור של משתמש קריאה בלבד, ואריץ את הבדיקה בעצמי. כך בודקים את ברירות המחדל של Supabase האמיתי.
6. **מה להעביר לי:**
   - **כתובת הפרויקט ומפתח anon:** מהמסך Settings → API. המפתח הזה ציבורי מעצם הגדרתו, והמידע מוגן ברמת השורה. מפתח `service_role` לא נמסר לעולם, ולא נכנס לאפליקציה או למאגר.
   - **בדיקה אוטומטית:** שמור את שני הערכים כ-Secrets בריפו: `STAGING_SUPABASE_URL` ו-`STAGING_SUPABASE_ANON_KEY`.
   - **בדיקה ידנית בטלפון:** במחשב שבונה את האפליקציה, צור קובץ `.env.local` לפי `.env.example`, עם `VITE_BACKEND_ENV=staging`. הקובץ הזה לא נכנס ל-Git, ובדיקת הסודות חוסמת אותו.
7. **חשבונות בדיקה:**
   - רק כתובות שנועדו לבדיקה, למשל `tester1@<הדומיין-שלך>`.
   - נתונים סינתטיים בלבד.
   - בלי משתמשים אמיתיים, עד שתאשר מדיניות פרטיות.

## מה ייבדק אחרי ההקמה

**בבנייה מותקנת על שני טלפונים**, ולא רק בשרת הפיתוח:
- הרשמה עם קוד;
- קוד שגוי וקוד שפג תוקפו;
- רענון session אחרי שעה;
- התנתקות, כולל במצב טיסה;
- שני מכשירים על אותו חשבון: רישום, מחיקה, תשובה שאבדה;
- ביטול הסכמה ומחיקת גיבוי;
- מחיקת חשבון ממכשיר אחד, ומה רואים במכשיר השני.

**על הפרויקט האמיתי:**
- ביקורת ההרשאות (סעיף 5);
- הרצה חוזרת של בדיקות המסד, דרך מחרוזת חיבור לפרויקט dev בלבד. הבדיקות יוצרות מסד זמני משלהן.

עד אז, כל זה נבדק מול תחליף מקומי. התחליף מריץ את קוד האפליקציה האמיתי (`supabase-js`) ואת PostgreSQL האמיתי עם המיגרציות, אבל הוא אינו Supabase עצמו. הפירוט בדוח הסבב.
