# מצוות+ | חבילת המשך לקלוד קוד

**תאריך בדיקה:** 23 בנובמבר 2026  
**מטרה:** להפוך את תוכנית הפיתוח המצורפת לתהליך עבודה שאפשר לבדוק, לקראת iPhone ו-Android.

## ההחלטה המקצועית

אפשר להמשיך בכיוון React + Capacitor + Supabase, בתנאי שזה אכן בסיס הקוד הנוכחי וששלב היתכנות על מכשירים אמיתיים עובר. המסמך המקורי אינו מספיק, כפי שהוא, כהוראה לבנות את כל המוצר ולהגישו לחנויות. יש פערים בתאימות, רישיונות, פרטיות, סנכרון, התראות וגישה לבדיקת החנויות.

החבילה היא ביקורת תכנון והצעת מפרט מתוקן. היא אינה קוד אפליקציה, בדיקת אבטחה של המאגר, אישור משפטי, אישור רבני או אישור חנויות. אין כאן טענה שהאפליקציה נבנתה, הותקנה או נבדקה במכשיר.

## איך ממשיכים

1. מחלצים את החבילה בתוך המאגר הקיים, למשל לתיקייה docs/mobile-readiness. אין להחליף את קוד האפליקציה בקבצים האלה.
2. פותחים את אותו מאגר ב-Claude Code.
3. מדביקים את תוכן 05_CLAUDE_CODE_START_HERE_HE.md.
4. קלוד מאמת קודם את המאגר וה-commit, ואז מתקדם לשלב ההיתכנות בהתאם לכלים ולהרשאות שיש לו.
5. כל בדיקה שלא רצה מסומנת NOT_RUN או BLOCKED. צילום דפדפן, build של Vite או סימולטור אינם הוכחה להתקנה מחנות.

## כללי קריאה

- **עובדה מאומתת:** דרישה או התנהגות שאומתה במקור רשמי בתאריך הבדיקה.
- **ממצא במסמך:** מה שהתכנון טוען; אינו מאמת שהמימוש קיים.
- **המלצה:** החלטה הנדסית או מוצרית מוצעת.
- **פתוח:** נדרשת בדיקת קוד, החלטת בעלים, גישה לחשבון או בדיקת מכשיר.

P0 הוא תנאי שחייבים לסגור לפני התחייבות לארכיטקטורה הרלוונטית או לפני פרסום. הוא אינו אומר שצריך לעצור את כל הפיתוח. P1 הוא תנאי לבטא או להגשה; P2 הוא הרחבה שאפשר לתכנן בנפרד.

ה-PDF המקורי בן 14 העמודים הוא התכנון שנבדק. המפרט המתוקן והחלטות בעל המוצר מתעדים את השינויים הנדרשים בו. אם נמצאת סתירה עם הקוד, מתעדים אותה; לא מבצעים שכתוב עיוור. דרישות חנויות משתנות ויש לאמת אותן מחדש לפני ההגשה בפועל.
