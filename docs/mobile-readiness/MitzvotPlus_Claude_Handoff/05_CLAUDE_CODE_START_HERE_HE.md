# מצוות+ | הוראת פתיחה ל-Claude Code

הדבק את תוכן הקובץ ב-Claude Code כשהמאגר פתוח. זו הוראה לביצוע ביקורת בסיס קוד ושלב היתכנות, ולא הצהרה שהבדיקות כבר עברו.

## המשימה

המשך את פיתוח MitzvotPlus לקראת אפליקציה לאייפון ולאנדרואיד. המאגר המיועד הוא https://github.com/nissank-coder/MitzvotPlus. המוצר מיועד למעקב מצוות בעברית, עם משחקיות בוגרת, חברתית ומכבדת. ארבעת מסכי הליבה הם 100 ברכות, דבר תורה, ניקוד והתקדמות, וטיימר שמירת הלשון.

קרא קודם את הוראות העבודה הקיימות במאגר, לרבות AGENTS.md ו-CLAUDE.md אם קיימים, ואת כל חבילת ההמשך: 00 עד 08 והתבניות. כבד את הוראות בעל המוצר. אל תחליף קוד או הוראות קיימות באמצעות החבילה. תעד סתירות בין הקוד, ה-PDF והמפרט המתוקן. החלטות המסומנות כהמלצה ב-06 אינן אישור של בעל המוצר.

בצע את G0 ואת G1 לפי מסמך שערי הקבלה. אל תסיים בהצעת תוכנית בלבד אם יש לך יכולת לבצע עבודה מקומית מאושרת. התקדם עצמאית בקריאות, בעריכות הפיכות, בבדיקות ובהכנת תוצרים לבדיקה. אין צורך באישור לכל פקודה. כשנדרשת החלטת מוצר או גישה חסרה, המשך במקביל בחלקים שאינם תלויים בה.

## G0: אימות המאגר והמצב הקיים

1. זהה מאגר, remote, ענף, commit SHA ושינויים שטרם נשמרו. שמור את עבודת המשתמש. צור ענף עבודה מבודד אם זה מתאים למצב המאגר ולהוראותיו. אל תבצע reset, ניקוי גורף או force push.
2. קרא package.json, קובץ נעילה, הגדרות בנייה, פרויקטים נייטיביים, אחסון וכניסות למסכים. קבע אם מדובר ב-React/Vite, Expo/React Native או מבנה אחר. אל תניח ש-15 מסכים או 38 בדיקות אכן קיימים רק משום שהם מוזכרים בתכנון.
3. הרץ את פקודות ההתקנה, בדיקת הטיפוסים, הבדיקות והבנייה המתאימות למאגר. השתמש במנהל החבילות ובקובץ הנעילה הקיימים. תעד כשל בסיסי לפני שינוי, כדי להבחין בינו לבין תקלה חדשה.
4. מפה את ארבעת המסכים ואת הנתונים המקומיים: מה עובד, מה דמה, מה חסר ומה חייב להישמר בהסבה. אל תסיר מידע קיים כדי לגרום לבדיקה לעבור.
5. מלא את מטריצת התאימות ואת מלאי הרישיונות. אמת דרישות משתנות מול המקורות הרשמיים והגרסאות שנבחרו. תעד תאריך בדיקה.

שמור דוח G0 עם ראיות בתיקיית docs/mobile-readiness/evidence או במיקום המקביל שכבר נהוג במאגר.

## G1: הוכחת המסלול במימוש קטן

אם הקוד הוא React DOM/Vite, בחן שימור הממשק והוספת Capacitor בגרסאות תואמות. אם הוא Expo/React Native, בצע הערכת התאמה לפני שינוי הארכיטקטורה. כתוב החלטה קצרה המבוססת על הקוד; אין לבצע שכתוב רק כדי להתאים את המאגר ל-PDF.

ממש חתך קטן שמוכיח:

- מסך ליבה בעברית RTL, נגיש ושימושי במכשיר.
- פעולה מקומית הנשמרת במסד הנתונים, עובדת offline ונשמרת לאחר סגירה ופתיחה.
- תוסף SQLite, migrations ואחסון מאובטח תואמים למערכת ולרישיון שנבחרו.
- מחזור חיים, מקלדת, אזורים בטוחים, ניווט וקישור שחוזר לאפליקציה סגורה.
- מסלול התחברות שנבחר, אם ניתן לבדוק אותו עם ההרשאות והחשבונות הקיימים.
- נתיב ההתראות המיועד להשקה, אם הוא נכלל בהיקף המאושר, לרבות הבחנה בין APNs ל-FCM. נתיב שלא הוכח יישאר כבוי.

הכן build חתום והתקן במכשירי iPhone ו-Android אמיתיים כאשר הכלים, החתימה והגישה זמינים. בדוק גם התקנה ממסלול הבדיקה הרלוונטי כאשר יש הרשאה לכך. צילום דפדפן, הצלחת Vite, סימולטור או mock אינם הוכחה לבדיקה במכשיר או להתקנה מחנות.

אם אין Mac/Xcode, מכשיר, חשבון מפתח, מפתחות חתימה או הרשאה לשירות, סמן את הבדיקה המתאימה BLOCKED והסבר מה חסר. המשך בהכנת קוד, בדיקות מקומיות ופקודות הרצה הניתנות לבדיקה. אל תסמן שער כמושלם בגלל הכנה בלבד ואל תבקש סודות בצ'אט.

## כללי מימוש מחייבים לסבב

- השתמש במפרט המתוקן לחוזי זמן, סנכרון, פרטיות, זהות ומחיקה. אל תציג ניקוד ממתין כסופי.
- באידמפוטנטיות, תשובה סופית נשמרת; deferred נבדק מחדש לאחר retryAfter. אסור לנעול אירוע לנצח בגלל ניסיון סנכרון בשבת.
- השתמש בנתוני בדיקה סינתטיים ובסביבה מבודדת. אין להמציא משתמשים פעילים, הסכמות, אישורי תוכן או תוצאות בדיקות.
- שמור טיימר שמירת הלשון מקומי לפי ההמלצה הזמנית, ללא טלמטריה רגישה. אל תרחיב איסוף מידע ללא החלטה מתועדת.
- אל תכניס מפתחות שרת, טוקנים או חומרי חתימה למאגר. אל תסמן מדיניות פרטיות, רישיון או הצהרת חנות כמושלמים בלי בדיקה.
- פרסום בחנויות, שינוי זמינות בפרודקשן או חשיפת מאגר ונתונים מחייבים החלטת בעלים והרשאה מתאימה. אם כבר קיימת הרשאה מפורשת לפעולה המסוימת, אין לבקש אותה שוב. אין לפרסם ציבורית כחלק מבדיקת היתכנות בלבד.
- אל תוסיף זיהוי בודקים, עקיפת שבת מוסתרת או הפעלת פיצ'רים לא מתועדת לאחר ביקורת החנות.

## התוצאה הנדרשת בסוף הסבב

דווח בקצרה מה התגלה ומה השתנה, עם ענף ו-commit או פירוט שינויים מקומיים. צרף נתיבים לתוצרים, החלטת הארכיטקטורה, גרסאות שננעלו ותוצאות הבדיקות. לכל בדיקה ציין PASS, FAIL, BLOCKED או NOT_RUN, יחד עם סביבה וראיה. השתמש בסטטוס המוגדר בתבניות אם הוא מפורט יותר.

עדכן את ה-backlog ואת שערי הקבלה. ציין רק החלטות וחסמים שמשפיעים על ההמשך, את הפעולה הבאה המומלצת ואת העבודה שאפשר כבר לבצע. אל תטען למוכנות לחנויות, לאישור Apple/Google או להשלמת מחיקה ואבטחה על סמך בדיקת קוד בלבד.
